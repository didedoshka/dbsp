# План эксперимента

## Проверяемый вопрос

На примере запроса проверяется, что инкрементальная программа выполняет работу, зависящую преимущественно от размера изменения и затронутого состояния, и поэтому выигрывает у полного пересчёта при достаточно малых обновлениях.

## Сравниваемые варианты и baseline

За baseline считается полный пакетный пересчёт.

Baseline: применяет изменения к таблицам и заново вычисляет весь запрос.

Собственный движок: обновляет сохранённое состояние по изменениям.

Feldera: выполняет тот же SQL-запрос.

Условия сравнения: одинаковые исходные таблицы, обновления, последовательность пакетов, среда исполнения


## Данные или нагрузки

Планируется написать генератор, который готовит таблицы из [плана проекта](project.md#запросы), количество строк в таблице считается параметром генератора, ключи генерируются равномерно из заранее известного диапазона. Затем генерируются обновления на основе полученной таблицы. Для первой точки генератор и серии не требуются; срок — КТ-2.

## Конфигурации и план запусков

Предполагаемые параметры генератора 
- `N` количество строк в таблице перед тестированием
- `batch_size` количество запросов в одном пакете
- 'k' количество пакетов


Диапазоны `N`, `batch_size` и `k` выберем по пробным запускам к КТ-2.

Конфигурация: Feldera 0.375.0 (revision `8270e156`) в Docker, `workers` по умолчанию, `storage` выключен (`storage: None`). Сейчас размер пакета — 1; размер пакета является параметром эксперимента.

Pipeline пересоздаётся при каждом запуске: stop, clear, delete, create, start. После выхода программы pipeline остаётся запущенным.

Число повторов: не менее 3 на конфигурацию.



## Метрики

`T`, мс — время исполнения `update` всех пакетов. В замер входит весь вызов `update`; для Feldera — вместе с ожиданием завершения шага. Вызовы `view` и сравнение результатов выполняются вне замера.

Для синхронизации Feldera `/ingress` возвращает completion token, `/completion_status` по нему отдаёт номер шага `step`, затем поток изменений читается до чанка с `processed_steps >= step`.

Пропускная способность, обновлений/с: `k × batch_size / T`.

Потребление оперативной памяти, MB, снимается после серии. Для своих движков источник — RSS процесса. Для Feldera рассматривается `/stats` (поле `memory` у endpoint) или метрики pipeline; источник peak memory нужно уточнить после первого замера.

Прирост скорости собственного движка и Feldera: `T_naive / T_x`.

Корректность исполнения (ожидается везде корректно)

Метрики могут быть изменены и/или дополнены ближе к тестированию основного запроса.

## Проверка корректности

Корректность проверяется за счет небольших тестов, которые можно отсмотреть руками, а также считать полный пересчет корректным исполнением.

После каждого обновления драйвер применяет его ко всем трём движкам и сравнивает их `view` как мультимножества. `ZSet<T>` — свой тип над `HashMap<T, i64>`; его равенство не учитывает нулевые веса, поэтому контракта на их отсутствие нет.

Хранилище у собственных движков общее: обе таблицы хранятся как индекс по ключу соединения. Разница только в алгоритме: naive пересчитывает `join` целиком, incremental соединяет дельты с индексами.

Планируются unit-тесты операторов с дельтами, выведенными вручную. 

## Обработка и анализ

Сохраняются измерения каждого запуска. Для каждой конфигурации рассчитываются медиана, минимум и максимум времени по повторам. Строятся графики времени, ускорения и памяти относительно размеров теста

Сценарий обработки будет добавлен вместе с получением первых результатов тестирования
